# 第十條對照表：條文的哪個字，對應這段的哪個欄位

**用途**：證券商向 AI 供應商要求「留存軌跡紀錄」時，這一頁說明本揭露段能交付條文的哪一部分、不能交付哪一部分。

**適用法源**：中華民國證券商業同業公會「證券商運用人工智慧技術自律規範」**第十條（落實可驗證）**。金管會 113 年 11 月 19 日金管證券字第 1130361481 號函准予備查；公會 113 年 11 月 21 日中證商業一字第 1130006063 號公告實施。

> ⚠️ 常見誤引：金管會 113 年 6 月 20 日「金融業運用人工智慧（AI）指引」**沒有**這項要求。該指引全文「軌跡」出現 0 次，且通篇為「宜」等建議性表述。強制性的「應」在公會自律規範，不在指引。

---

## 條文逐字

**第一項（自行開發）**
> 證券商自行開發、優化人工智慧技術時，**應**保存必要技術文件及相關紀錄，包括開發者在設計、開發和實施過程中，**如為可能影響決策的重要資料、模型或演算法等紀錄**，以確保其在必要時**可被查驗**。

**第二項（使用第三方）**
> 證券商使用第三方人工智慧技術時應執行調查、評估及監督作業，**以確保第三方業者在人工智慧運算有留存軌跡紀錄，俾利後續查驗**。

「軌跡」二字在整份規範只出現這一次，位置在第二項。義務主體是證券商，但履行方式是「確保第三方業者留存」，因此實際交付物由 AI 供應商產出。

## 逐句對照

| 條文文字 | 對應到什麼 | 由誰承載 |
|---|---|---|
| 第三方業者 | 簽發者身分 | **宿主格式**（VC 的 `issuer`、DSSE 的簽章金鑰） |
| 在人工智慧運算 | 一次決策一份紀錄 | **宿主格式**（收據本體） |
| 可能影響決策的重要資料 | `relationships[]`：存在哪些付費關係 | **本段** |
| 可能影響決策 | `effect.kind`：該關係對這次決策做了什麼（`ranking` / `inclusion` / `exclusion` / `filtering` / `presentation` / `none`） | **本段** |
| 留存軌跡紀錄 | `compensation`：金額或費率，或明示 `withheld` 而非留白 | **本段** |
| 俾利後續查驗 | 可離線驗證簽章 | **宿主格式** |
| 俾利後續查驗 | schema 驗證：格式合規可機器判定，不需人工閱讀 | **本段** |
| 可被查驗 | `completeness`：簽發者具名宣告清單是否完整，漏報即為可歸責的不實陳述 | **本段** |

## 實例：券商 AI 推薦基金

假設 AI 助理推薦了一檔基金，該基金的代銷商付給券商 0.75% 的分潤。

```json
{
  "spec_version": "0.1.0",
  "completeness": "complete",
  "relationships": [
    {
      "id": "fund-distributor",
      "counterparty": { "ref": "distributor.example", "kind": "merchant" },
      "direction": "inbound",
      "form": "revenue_share",
      "compensation": { "type": "rate", "rate": 0.0075 },
      "effect": { "kind": "inclusion", "targets": ["opt:fund-c"] },
      "disclosed_to_principal": "in_band"
    }
  ]
}
```

主管機關事後查驗時，這份紀錄回答了三個問題：**有沒有利益關係**（有）、**影響了什麼**（該檔基金因此被納入推薦）、**券商當時有沒有告知客戶**（有，在推薦當下）。三個答案都在簽章涵蓋範圍內，不能事後修改而不被發現。

若該次推薦確實沒有任何付費關係，正確做法是送出空陣列而非省略本段：

```json
{ "spec_version": "0.1.0", "completeness": "complete", "relationships": [] }
```

空陣列是「經簽章的無利益衝突聲明」，省略則什麼都沒主張。這個區別在事後查驗時是決定性的。

## 本段做不到什麼（先講，不要賣過頭）

第十條第一項要求保存的是「**重要資料、模型或演算法**等紀錄」。付費影響只是其中一類，而且是現行工具最不會記錄的一類。以下**不在本段範圍**，需要由宿主收據格式或其他工具涵蓋：

- 模型版本、供應商、參數
- 輸入資料與其來源、prompt 內容
- 推論過程、考慮過哪些選項（既有規格 Signatrust ADR v1.0 的 `domains_evaluated` / `domains_excluded` 已涵蓋此項）
- 保存年限與儲存位置（規範未定，由券商內控政策決定）

另一項限制必須對法遵人員講清楚：**簽章能證明紀錄未遭竄改、能證明是誰簽的，但不能證明沒有漏報。** 本段的 `completeness` 欄位是在沒有可信第三方的前提下所能做到的最強保證：它讓漏報從「沉默」變成「具名的不實陳述」。若要進一步收斂，需要付款方共簽、透明日誌或主管機關抽查，三者皆不在 v0 範圍內。

其中主管機關抽查正是第十條所要求的「必要時可被查驗」，也就是說：**這條規範本來就把最後一道防線放在查驗，而不是放在技術保證。** 本段的設計與該前提一致。
